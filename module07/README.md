この設計によって利用者側は具体的なcreature へ強いく依存しなくなる

「Abstract Factoryとは何ですか？」
関連するオブジェクト群を、具体的なクラスを利用側へ意識させずに生成するパターンです。
今回の関連オブジェクト群は、同じファミリーの進化前・進化後です。利用者は具体的なモンスターの作り方ではなく、どのファミリーのfactoryを選ぶだけかを意識すれば良い

heal, transform はcreature から独立した抽象クラス
具象creature がcreature とcapablityを多重継承することで基本的なcreature の動作に追加能力を組み合わせてる
基本機能と追加能力を分離し、多重継承で組み合わせる
インスタンス属性の変数

戦い方ごとの行動手順をStrategyクラスにまとめ、その戦い方をCreatureが実行できない場合に専用例外で処理する仕組みを作った
Strategyパターンは、アルゴリズムや行動手順を別クラスへ分離し、実行時に交換できるようにするパターンです。今回、Creatureが誰かと、どう戦うかを分離しています。トーナメントはstrategy.act(creature)を呼ぶだけで、具体的な戦闘手順を知りません。
「なぜパターンを使うの？」と聞かれたら
次のように答えられます。
生成、能力、戦闘手順を別々のクラスへ分けることで、それぞれの変更が他の部分へ影響しにくくなるからです。新しいCreatureファミリーならFactory、新しい能力ならCapability、新しい戦い方ならStrategyを追加できます。

これは「変更理由が違うものを分離する」という考え方です。
「デメリットは？」と聞かれたら
メリットだけでなく、次も説明できると良いです。
クラスやファイルの数が増える
小規模な処理では直接書くより複雑に見える
抽象化が過剰だと理解しにくくなる
多重継承では初期化順序やMROに注意が必要
FactoryやStrategyの選択自体は、どこかで行う必要がある
今回の課題は小規模ですが、大規模化した場合の変更しやすさを体験するためにパターンを使用しています。
変更が起きたときどこまで影響が波及するかがデザインパターンの着眼点
変更に強い設計のための定石集がデザインパターン
